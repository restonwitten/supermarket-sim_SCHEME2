- Define the fixture as a sequence of named states (e.g., S0, S1, ...), each

Testability requirements for the contract:

- Monitoring API. Specify, as clauses: named modules for the model and for the
  monitoring runtime; violation exceptions that carry clause_id; selectable
  assertion levels with a context manager that restores the previous level, and a
  check_invariants(obj) function; that the precondition reported is the first
  false one in the routine's table order, raised before any state changes; that
  the lowest level checks nothing and is used only to build counter-example
  objects; that every ensure and invariant clause has a pure, callable predicate
  named after its clause ID; and that each predicate reads only the queries its
  clause names, so a stub object can stand in for a state the constructors cannot
  build.
- Creation procedures. Give every class an explicit creation procedure with its
  own clauses and examples. Build containers bottom-up: a container's constructor
  takes finished, unattached children and becomes their parent.
- Frame conditions. Provide the queries needed to state and test "nothing else
  changes" postconditions, such as a snapshot of the model's mutable state as one
  comparable value, existence checks used by preconditions, and ID counters.
- Outcome reasons. Where a result reports a reason (such as why a SKU was not
  placed), the reasons are mutually exclusive, with a stated precedence order.
- IDs. Each ID prefix belongs to exactly one class. IDs of created records are
  sequential and never reused.
- Deterministic allocation. The allocation function has exactly one correct result
  for given inputs, specified by a canonical rule, so examples can assert exact
  placements. Property-style postconditions stay as independently checkable
  clauses that the canonical result satisfies.
- Grounding index. Include an appendix indexing every clause by grounding tag
  ([TB], [VS], [DISC], [SIM]).
